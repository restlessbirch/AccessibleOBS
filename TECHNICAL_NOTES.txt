Accessible OBS — technical notes
================================

Reference for anyone working on the code. Describes how the parts fit
together and which constraints are imposed from outside.


Binaries
--------
bin\bootstrap.exe — first-time setup, console application.
  --launcher          accessible launch menu; the default mode for
                      AccessibleOBS.exe in the release archive.
  --host              Tailscale + OBS + WebSocket password + host agent +
                      autostart registration + pairing code.
  --controller        Tailscale + locate the agent in the tailnet + open
                      the browser.
  --local             local accessible mode, no Tailscale and no pairing code.
  --remove-autostart  remove the autostart shortcut.

bin\host-agent.exe — background agent, HTTP API and panel static files.
  Release builds use windows_subsystem="windows", so no console window
  appears: the agent starts at logon and a flashing console would be
  noticeable. Debug builds keep the console.


Connection to OBS
-----------------
One persistent WebSocket connection per process (src/obs.rs).

A background task owns the socket, performs the handshake once and routes
replies back by requestId through oneshot channels.

  - reconnect with exponential delay, 0.5 to 15 seconds, reset after any
    connection that was actually established;
  - while there is no link, commands are rejected immediately instead of
    waiting for a timeout;
  - request timeout 10 seconds;
  - WebSocket Ping every 20 seconds to detect a dead channel;
  - RequestBatch (op8) for bulk operations;
  - event subscriptions delivered to listeners through a broadcast channel;
  - close code 4009 is reported as a wrong password in plain language.

Note that op9 is RequestBatchResponse, not an authentication failure.


Event stream to the panel
-------------------------
GET /api/events — Server-Sent Events, requires authentication.

Message types:
  {"type":"obs","event":{...}}                  OBS events, verbatim
  {"type":"obs_status","status":{...}}          link to OBS gained or lost
  {"type":"levels","levels":{...}}              audio levels, throttled
  {"type":"donation","donation":{...}}          new donation
  {"type":"donationalerts_status", ...}         donation feed state
  {"type":"chat","author":...,"text":...}       Twitch chat message
  {"type":"alert","alert":{...}}                frame drops, disk space
  {"type":"resync_required","lost":N}           events were dropped

The panel redraws affected sections with a 250 ms delay so that a burst of
events does not produce a burst of requests.

Authorisation is not checked only at connection time. Each session change —
sign-in, sign-out, expiry — increments a session generation counter, and any
stream opened under a previous generation closes itself.

/api/obs/request is a narrow compatibility endpoint for read-only requests
still used by the frontend: GetStreamStatus and GetRecordStatus. Every other
OBS command goes through a dedicated API route.

The actor display for a second monitor uses view-only routes:
  GET  /api/actor-display/state
  GET  /api/actor-display/events
  POST /api/actor-display/open
  POST /api/actor-display/project

These skip the panel session only for a loopback request that also passes the
Origin/Host check, so the browser on the actor's machine can show
display.html. Anything else requires a normal authenticated session.


Network model
-------------
- No Tailscale auth keys.
- No port forwarding.
- The agent listens on both the Tailscale address and 127.0.0.1.
  Loopback is not a convenience: the DonationAlerts OAuth redirect_uri points
  at 127.0.0.1, and without that listener the authorization code would never
  reach the agent. The loopback interface is unreachable from outside.
- If no Tailscale IP is available, the agent stays on loopback only and logs
  a warning.


Panel authorisation
-------------------
- Pairing code: 10 random bytes, base64url, stored through DPAPI.
- Code and session token comparisons are constant-time
  (subtle::ConstantTimeEq).
- Five consecutive failures block sign-in for 30 seconds, counted per peer
  address rather than globally.
- Every successful sign-in issues a new session token.
- Session tokens have a 2 hour idle TTL and a 12 hour absolute TTL. Tokens in
  the older format, which carried no timestamps, are discarded at startup.
- The session token is cached in memory rather than decrypted per request.
- Cookie is HttpOnly, SameSite=Lax. Secure is deliberately not set: traffic
  inside the tailnet is http and encrypted by WireGuard at the network layer,
  and with Secure the browser would discard the cookie entirely.
- POST /api/auth/logout ends the session and closes open event streams.
- DonationAlerts OAuth uses a single-use state parameter.

Every response carries frame-ancestors 'none', X-Frame-Options: DENY,
referrer-policy and nosniff. Origin checks alone do not stop framing: a script
inside an iframe runs as the panel's own origin, so its requests would pass.

The launcher on 127.0.0.1:8786 checks request origin and a one-time token
generated per launch. Its POST routes start programs and remove autostart, and
a plain HTML form from another page is enough to reach localhost otherwise.


Secret storage
--------------
config\secrets\*.dpapi, Windows DPAPI, CurrentUser scope:
  obs_websocket_password, pairing_secret, session_token,
  donationalerts_widget_url, donationalerts_tokens,
  donationalerts_client_secret, twitch_tokens, twitch_device_code.

If donationalerts.client_secret is placed in config\host.json temporarily, the
agent migrates it into donationalerts_client_secret.dpapi at startup and
rewrites host.json with an empty field.

The obs-websocket password additionally lands in the OBS configuration,
because OBS will not accept it otherwise. That is an OBS constraint, not a
project choice.


Third-party installers
----------------------
third_party\installers.json pins the version, URL and SHA-256 of OBS Studio
and Tailscale. Both the release packaging script and first-time setup read the
same manifest, download only from the pinned URL and verify the hash before
executing anything. A file shipped inside the archive is verified too — it has
been sitting on disk since the release was built.

A hash mismatch is a refusal, not a warning, and the offending file is
removed.


OBS configuration on the actor's machine
----------------------------------------
obs-websocket settings live at:
  %APPDATA%\obs-studio\plugin_config\obs-websocket\config.json

This is not global.ini. Since OBS 28 the plugin is bundled and keeps its
settings here. Verified against OBS 32.2.1 with obs-websocket 5.7.4.

Keys managed by the project: server_enabled, auth_required, server_port,
server_password, first_load. Everything else, alerts_enabled for example, is
left untouched — those belong to the user.

An existing OBS password is adopted rather than replaced: Streamer.bot, Touch
Portal and other controllers may already be configured against it.

Order during setup: install OBS, write config.json, then start it. OBS reads
plugin settings at startup and rewrites the file on exit, so writing is only
meaningful while OBS is closed. If OBS is running and settings must change,
setup asks for it to be closed and waits up to 60 seconds.

Crash sentinels:
  %APPDATA%\obs-studio\.sentinel\run_<uuid>

OBS creates one per launch and removes it on a clean exit. A surviving file
makes the next launch show a safe-mode dialog that waits for somebody at the
keyboard. There is nobody at the actor's machine, so a single crash would cost
remote control until a person walked over. Sentinels are therefore cleared
before launch (clear_obs_crash_sentinel).

The trade-off is deliberate: a plugin that crashes OBS at startup produces a
crash loop instead of a safe-mode offer. So the crash is not swallowed — it is
reported through /api/health as obs_crashed_last_run and shown in the panel.

POST /api/obs/launch starts OBS on request and cancels the reconnect delay
through ObsHandle::reconnect_now(), so the panel does not wait out a backoff
that is already irrelevant.


Readiness check
---------------
src/preflight.rs is pure logic: a snapshot in, a list of checks out. No calls
to OBS, so it is fully covered by tests.

It answers "can this go on air", not "does OBS respond":

  - OBS connection and configured stream key;
  - current program scene contents, following nested scenes and groups;
  - whether visual sources are genuinely active, via GetSourceActive;
  - whether the composed frame is anything other than black — the agent
    requests a 64x36 uncompressed BMP and looks at the brightest pixel,
    because a capture source can report itself active and still produce
    nothing;
  - microphone assignment, mute state and live level;
  - system audio capture that would broadcast the operator's screen reader;
  - free disk space while recording;
  - Twitch connection and donation overlay state.

An unknown result is reported as unknown, never as a pass.


DonationAlerts
--------------
Donation announcements are produced by the official Alerts Widget, not by this
code. Reconcile brings OBS to a working state and is idempotent:

  - scene RSC_OVERLAYS;
  - browser_source RSC_DonationAlerts;
  - url, width/height from the OBS canvas, reroute_audio=true,
    shutdown=false, restart_when_active=false;
  - volume -8 dB on first creation;
  - audio monitoring from the monitoring setting, defaulting to both the
    stream and the owner: a blind streamer has no other signal that a
    donation arrived;
  - RSC_OVERLAYS nested in every user scene and raised to the top layer;
  - a conflict is reported if RSC_DonationAlerts is taken by a source of a
    different kind.

Widget URLs are accepted over https only. The widget is always served over
https, so http would mean a typo or a substitution.

Reconcile does not trust the commands it sent. It re-reads OBS and checks mute
state, volume, monitoring type, audio routing and the configured URL, because
each of those failing silently makes donations inaudible in a different way.

Realtime feed (src/donationalerts.rs), Centrifugo:
  GET /api/v1/user/oauth  ->  socket_connection_token
  wss://centrifugo.donationalerts.com/connection/websocket
  POST /api/v1/centrifuge/subscribe  ->  channel signature
  token refresh through refresh_token


Twitch
------
Device Code OAuth, tokens stored through DPAPI, validation through
/oauth2/validate, reading and changing channel settings, stream markers.

Chat is read anonymously with a justinfan nickname and needs no token at all,
so it works before OAuth is completed. Messages are rendered as ordinary page
elements rather than an embedded widget: a screen reader reads a foreign
iframe poorly and never announces new messages.

A validated token is cached for a minute. The panel asks for state after every
operator command, and each of those would otherwise cost a network round trip
to Twitch.


Logging
-------
logs\host.log and logs\bootstrap.log, rotated daily, seven files kept.

Diagnostics reads the tail through a seek in a blocking task rather than
loading the file: the agent runs for months and the runtime has two worker
threads.

Secrets never reach the log. Panel-side errors are posted to
/api/client-error so browser failures land in the same file as the agent's.


Autostart
---------
Shortcut "Accessible OBS.lnk" in the user's Startup folder
(%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup), created through
WScript.Shell. A shortcut rather than a Run registry key: it is visible to the
user, can be deleted by hand and needs no administrator rights.

Shortcuts left by earlier names of the program are removed, otherwise two
agents would start at logon and the second would fail to bind the port.

The agent starts OBS itself when auto_start_obs=true.


What cannot be verified without real accounts and hardware
----------------------------------------------------------
- acceptance of a Twitch client_id by a real application;
- exchanging a DonationAlerts client_secret for tokens;
- Centrifugo channel details for a specific account;
- browser_source availability in the OBS build on the actor's machine;
- MagicDNS naming and Windows firewall policy in a specific tailnet.

These paths are written against the documentation and covered by unit tests
for parsing and state handling.
